BAGIAN 1

Studi Kasus & Latar Belakang (Domain Pabrik Baja)

Q1 Kenapa Anda membuat sistem ini dan apa masalah utama yang diselesaikan di PT Garuda Yamato Steel?
Jawaban Ringkas & Tepat: "Sistem ini dirancang khusus untuk tim Mechanic Engineer di PT Garuda Yamato Steel. Masalah utamanya adalah pencatatan manual suku cadang mekanik yang rentan tercecer atau lambat ditemukan saat terjadi breakdown mesin pabrik. Sistem ini mempermudah pencatatan stok fisik aktual dan memetakan langsung posisi barang pada nomor rak serta lokasi gudangnya, sehingga waktu penanganan perawatan/perbaikan mesin (maintenance downtime) dapat dipangkas secara signifikan."
💡 Kunci penilaian: Dosen ingin tahu apakah sistem memiliki dampak nyata terhadap efisiensi operasional pabrik.
Q2 Siapa pengguna utama dari sistem ini?
Jawaban Ringkas & Tepat: "Pengguna utamanya terdiri dari dua pihak:
  1. Staf Gudang Mekanik (Storekeeper): Bertanggung jawab melakukan input registrasi sparepart baru, pembaruan stok fisik, dan penataan posisi rak.
  2. Teknisi / Mekanik Maintenance: Memeriksa ketersediaan suku cadang dan mengetahui lokasi rak penyimpanan secara presisi saat butuh pergantian komponen mesin."
BAGIAN 2

Arsitektur Laravel & Konsep MVC

Q3 Jelaskan bagaimana konsep MVC (Model-View-Controller) berjalan pada fitur Tambah Barang di web Anda!
Jawaban Ringkas & Tepat: "Alur MVC berjalan secara terpisah dan terstruktur:
  • View (create.blade.php): Menyediakan antarmuka form input data barang dan pilihan rak untuk pengguna.
  • Controller (BarangController@store): Menerima data HTTP POST, melakukan validasi kelayakan data (nama, stok, id_rack), dan memproses penyimpanan.
  • Model (Barang.php & Rack.php): Bertugas berkomunikasi langsung dengan tabel database menggunakan Eloquent ORM untuk mengeksekusi perintah INSERT, lalu Controller mengalihkan (redirect) kembali ke View index dengan flash message sukses."
Q4 Kenapa memilih framework Laravel dan bukan PHP Native atau framework lain?
Jawaban Ringkas & Tepat: "Laravel menyediakan standar industri yang mempercepat pengembangan dan menjaga keamanan aplikasi:
  • Keamanan Bawaan: Terlindungi secara default dari CSRF, SQL Injection (melalui parameter binding PDO), dan XSS sanitization pada Blade.
  • Eloquent ORM: Mempermudah manajemen relasi antar tabel tanpa perlu merangkai sintaks SQL mentah secara manual.
  • Modular & Skalabel: Memudahkan integrasi fitur lanjutan di masa depan seperti autentikasi, export laporan, dan RESTful API."
BAGIAN 3

Basis Data & Relasi Entitas

Q5 Bagaimana hubungan/relasi antara tabel barang dan tabel rack?
Jawaban Ringkas & Tepat: "Hubungannya adalah One-to-Many (dari sisi barang: Many-to-One). Satu rak penyimpanan dapat menampung banyak item barang, sedangkan satu barang hanya dialokasikan pada satu rak tertentu. Di model Barang, relasi ini didefinisikan dengan metode $this->belongsTo(Rack::class, 'id_rack', 'id_rack'), di mana kolom id_rack bertindak sebagai Foreign Key."
Q6 Kenapa Anda membuat tabel rack terpisah dan tidak digabungkan langsung di tabel barang?
Jawaban Ringkas & Tepat: "Untuk menerapkan kaidah Normalisasi Database (2NF & 3NF) guna mencegah terjadinya anomali data dan redundansi. Jika nama rak dan deskripsi lokasi disimpan langsung di tabel barang, informasi lokasi yang sama akan tertulis berulang kali pada ribuan baris sparepart. Dengan tabel terpisah, pembaruan tata letak rak cukup diubah pada satu baris di tabel rack."
BAGIAN 4

Pertanyaan Kritis & Sorotan Kode (Code Review)

Q7 Di BarangController index, Anda menulis Barang::latest()->get(). Apakah ada potensi masalah performa saat menampilkan nama rak?
Jawaban Solutif & Cerdas: "Benar Pak/Bu, pemanggilan $barang->rack->nama_rack di dalam perulangan view berpotensi menimbulkan N+1 Query Problem. Artinya, sistem menjalankan 1 query awal untuk mengambil semua barang, lalu mengeksekusi N query terpisah untuk mengambil data rak setiap baris barang. Solusi optimasi yang tepat adalah menerapkan Eager Loading dengan mengubah kodenya menjadi:
$barangs = Barang::with('rack')->latest()->get();
Dengan demikian, seluruh data barang dan rak berelasi dimuat sekaligus hanya dalam 2 query SQL yang sangat efisien."
⭐ Poin Emas: Jika Anda menyebut istilah N+1 Query dan Eager Loading, dosen akan langsung tahu Anda menguasai backend secara mendalam.
Q8 Kenapa method edit() dan update() di BarangController belum diimplementasikan?
Jawaban Taktis: "Fokus pada tahap pertama pengembangan ini adalah memvalidasi modul penerimaan barang baru (Create), pemantauan ketersediaan stok fisik & pemetaan rak (Read), serta pembersihan data invalid (Delete). Modul pengubahan data (Update) beserta pencatatan riwayat kartu stok masuk-keluar (stock mutation log) merupakan rencana pengembangan pada modul fase kedua berikutnya."
Q9 Kenapa rute pada routes/web.php belum memiliki autentikasi (Login)?
Jawaban Taktis: "Pada tahap pengujian fungsionalitas lokal (development), rute dibuka untuk mempercepat uji coba alur kerja data. Namun untuk tahap deployment di lingkungan pabrik, sistem telah disiapkan untuk diintegrasikan dengan middleware auth Laravel serta pemisahan hak akses bertingkat (Role-Based Access Control) antara Admin Logistik dan Teknisi Lapangan."
BAGIAN 5

Keamanan & Integritas Data

Q10 Apa fungsi dari tag @csrf di formulir tambah barang?
Jawaban Ringkas & Tepat: "Fungsinya untuk menangkal serangan Cross-Site Request Forgery (CSRF). Directive @csrf menyisipkan input tersembunyi berisi token acak terenkripsi yang unik per sesi pengguna. Server Laravel akan memverifikasi kecocokan token ini untuk memastikan permintaan POST benar-benar berasal dari interaksi formulir sah pada sistem kita, bukan manipulasi skrip dari situs luar."
Q11 Mengapa aksi hapus barang menggunakan form dengan @method('DELETE') dan bukan link <a> biasa?
Jawaban Ringkas & Tepat: "Ada dua alasan mendasar:
  1. Standar HTTP RESTful: Operasi penghapusan data harus menggunakan kata kerja HTTP DELETE. Link <a> biasa menggunakan method GET yang berbahaya karena dapat terpicu secara tidak sengaja oleh bot web crawler atau prefetching browser.
  2. Method Spoofing: Karena form standar HTML hanya mendukung GET dan POST, directive @method('DELETE') memberitahu Laravel untuk memperlakukan request tersebut sebagai HTTP DELETE yang sah dan terlindungi CSRF."
Q12 Bagaimana validasi data dijalankan saat input barang?
Jawaban Ringkas & Tepat: "Validasi dieksekusi di method store() dengan fungsi $request->validate(). Ketentuannya:
  • nama_barang: Wajib diisi, bertipe teks, maksimal 255 karakter.
  • stock: Wajib diisi dan harus berupa angka bilangan bulat (integer ≥ 0).
  • id_rack: Wajib diisi dan harus valid terdaftar pada tabel rak (exists:rack,id_rack).
Jika aturan dilanggar, Laravel secara otomatis membatalkan transaksi dan mengembalikan input beserta pesan error ke form antarmuka."
BAGIAN 6

Fitur Antarmuka & User Experience (UX)

Q13 Bagaimana fitur pencarian barang pada tabel bekerja? Apakah melakukan query ke database lagi?
Jawaban Ringkas & Tepat: "Pencarian pada tabel bekerja secara Client-Side menggunakan JavaScript DOM Event Listener (input event). Skrip menyaring langsung teks pada setiap baris tabel yang telah dimuat di browser. Pendekatan ini dipilih karena memberikan pengalaman pencarian instan (real-time tanpa jeda loading halaman) dan meringankan beban query server."
Q14 Apa maksud dari 4 kartu indikator (KPI) di atas tabel barang?
Jawaban Ringkas & Tepat: "Kartu tersebut berfungsi sebagai ringkasan eksekutif inventaris mekanik:
  • Total Jenis Barang: Jumlah varian sparepart yang terdaftar dalam katalog.
  • Total Unit Fisik: Akumulasi jumlah kuantitas stok seluruh barang di gudang.
  • Perlu Perhatian: Menghitung otomatis barang yang stoknya kritis (≤ 5 unit) agar tim mekanik segera membuat permintaan pengadaan (purchase requisition).
  • Rak Terpakai: Jumlah titik rak aktif yang sedang terisi sparepart."
